# Engine playbook

Methods kept from running a team of AI agent lanes on a real production. Project-neutral: swap "deliverable" for whatever your team ships (a game, an app, a campaign). One entry per method: problem · method · gate · proof to collect.

## The idea

The lanes, their skills, pattern cards, gates and the tower are together an **engine**: whatever request goes in, a production-grade result should come out in as few rounds as possible. The human sets the goal and judges the result. The hub agent owns the processes (adds, cuts, reorders them) and changes them from the human's feedback, without asking for a review of the process itself. The aim is to make a non-deterministic engine (an LLM) behave deterministically by fixing the method, not the model.

## Engine flow: every task, every lane

Each step is a gate.

1. **Classify.** Name the task's deliverable type (a row in your `pattern-library.md`) and the process stage it is. A task that fits no row first gets a row.
2. **Two readiness checks.** (a) Is the process for this type confirmed? (b) Is the pattern card for this stage confirmed? Both live in the skill of the discipline that owns the work, whichever lane runs them.
3. **Missing means prepare first.** Process: the owning lane splits the work into stages; the hub reviews and confirms. Pattern card: collect references and techniques, write the recipe, test it in fresh sessions until it gives the same quality three times out of three. Production waits; the preparation is the task.
4. **Make, report, feedback.** The lane runs the stage by its card; the hub reviews against the card's checks; every human verdict and every failed review becomes a proposed card or process change (version bump).
5. **Rate the line.** Each stage carries a rating: first-pass rate over n tasks, per model, from a ledger of tasks and send-backs. Tune the lowest-rated stage first, one change at a time (split it, improve its card, change its model).

`stage_table` in `tower.json` connects step 1 to the model choice below: the same table row that names a type can carry a `Model · effort` column.

## Entries

- **Process card, then pattern card.** Problem: each task reinvents its method, so quality swings by session. Method: (a) a *process card* per deliverable type lists the ordered stages, each with input, output artifact, pattern card, gate, and who passes it (lane, hub, human); (b) a *pattern card* per stage is built by collecting shipped references with numbers, writing the recipe (regularities with spread, steps, checks, what is refused and why), then testing for sameness across fresh sessions. Gate: no stage runs without both cards, unless the brief marks it as finishing an already approved artifact. Proof: first-pass rate per stage.
- **Revision is a process too.** Problem: fixes after a verdict ran as free-form tells, so the same verdict got a different fix each time. Method: a send-back runs a short fixed procedure: R1 map what the verdict touches against the process stages, R2 find the stage that let it through, R3 propose the corrected line (and the card change), R4 redo only the affected stages, R5 report the map with the result. Gate: a send-back without R1's map is not accepted as done.
- **Reference analysis before making.** Problem: references attached as mood pictures after the idea prove nothing. Method: before any proposal, write the jobs the thing must do (ranked); pull at least three shipped works of the same type, each a real capture with source and date; note per reference how it solves each job and take or refuse it with a reason; every top job is solved by at least two references; the proposal names the reference ids it combines. Gate: no reference without a capture and a take/refuse line; requirements come from your jobs, never from a reference.
- **Part lanes with discipline chapters.** Problem: lanes cut by discipline (design, code, screens, art) split one request across lanes; each hand-over queued the work again and lost words. Method: one lane per part of the product owns design, art and code for its element, so a request opens and closes in one lane. Each discipline stays as a chapter: the skill that holds its process and pattern cards, loaded by whichever part needs it. Measuring and checking stay separate lanes so the maker does not grade its own work. Each chapter keeps one route per kind of job: the process cards in order, across chapters where needed, ending at the build or the measuring lane.
- **Hand-over note, not a summary, at a context swap.** Problem: when a long session is swapped for a fresh one, a free-form summary weighs every fact the same and drops rules (measured in the literature: rules survive about half after one summary, a tenth after five). Method: the outgoing session writes at most 12 lines in fixed slots: `[now]` step, why, next action · `[plan]` remaining steps, each acceptance criterion as pass/fail/unchecked with evidence path · `[files]` paths only · `[items]` open decisions · `[skills]` instruction files to reload. The original brief rides the resume prompt verbatim; rules come back from the instruction files, never from the note. In this repo: `tower report handoff "…"`.
- **The hub sets model and effort per task; small before strong.** Problem: one lane-wide model overpays for clear work and underpowers taste work, and a lane calling a stronger helper mid-task makes it reread the context. Method: every brief carries `model:` and `effort:` lines; the hub starts from the stage's cell in the process table and gives one reason to depart. Strong model at high effort for new design or taste calls, work a smaller model failed once, and refactors with hidden coupling; the smaller model at high effort for clear specs with judgment inside, at medium for clear specs carried out. Split first: a hard part becomes its own strong-model task. Gate: with `require_model_lines`, `tower task` refuses a brief without both lines. Proof: first-pass rate and tokens per deliverable.
- **Daily scope, evening build, joint review.** Problem: planning drifts when the day has no fixed scope, and playing the result reveals better directions. Method: each morning the hub writes the day's scope by the value it grows; the evening build carries it; the hub tries it first and posts one review (landed against plan, good, lacking, fix with a reference, three questions, tomorrow's draft); the human tries it at a fixed hour and the two agree the next day's scope. Gate: nothing new queued for tomorrow before the review is answered.
- **Hypothesis, then fast build, then the human tries it.** Problem: ideas wait on approval rounds and get judged on paper. Method: any idea that looks worthwhile goes in with a written hypothesis (which principle predicts it, a reference scene, what would prove it wrong), the smallest working version and a measurement; the human tries it in the next build and keeps, tunes or drops it. Gate: hypothesis and reference written before the build; working labels only until it is kept.
- **Asset method table.** Problem: lanes reach for the same generator for every asset; the hard assets eat the budget while code-shaped assets get made as images. Method: every asset brief names its row in a table of asset type, first-choice route and fallback, easy or hard for agents, and the verdict from a bake-off; a different route needs one line of why. Gate: no paid generation for an asset whose row says code or library. Typical rows: effects, shaders, outlines (code, measure frame cost); simple props (script-built, generator for organic shapes); characters (approved concept, multi-view generator, polish, standard rig); sound (paid pilot then batch, library fallback, always a listening check).
- **Route bake-off for a first-time asset type.** Problem: the table's first choices are guesses until tried. Method: the first task for a type whose verdict is open runs both routes on one small piece with the same acceptance criteria, (A) built by the agent in code, shader or script, (B) a generator makes the resource first and code goes on top. Compare: passes review at the size it is used, rounds to pass, tokens, money, runtime cost, ease of change. The hub writes the winner and evidence path into the verdict column. A verdict reopens only when a tool changes a lot or the winner fails the same check twice. Gate: the paid side stays inside an approved estimate; one small piece, never the whole set.
- **Measure before the human tries a rule.** Problem: rules reached the build judged as "it works". Method: keep a ladder of automated players on the same seeds, from random to committed-and-optimal, and model the economy on a sheet first. Gate: nothing goes to the human's build unless the ladder is strictly ordered with the stated margins and careless play loses to careful play.
- **Factory checks.** Limit samples per type; check the reviewer against the owner's verdicts (gauge check); a defect seen twice becomes a tool check (mistake-proofing); inspect stage inputs on arrival; stop the line when a check fails instead of passing it on.
- **Process hygiene on one machine.** Problem: long agent sessions grow to several GB each and a stuck capture can fill the disk; a memory guard then holds every lane. Method: a watcher renews any agent session over a memory line when its lane is idle (hand-over first) and stops orphaned engine, editor and capture processes after a set time; capture scripts quit on the first script error. Gate: no lane held by memory for more than ten minutes in a week.
- **Model-upgrade audit.** Problem: instructions, tools and docs pile up faster than anyone rereads them. Method: each time a stronger model comes out, one standalone session on it reads the whole repo, fixes only what is certain and safe (broken paths, dead files with grep proof, lines that contradict a recorded decision, bugs with a test) and lists the rest by severity and owner; the hub turns the list into tasks. Gate: tests green; no content or names touched.
- **Never ask twice, never poll.** Lanes run unattended. A question that needs a human becomes a board item; the answer arrives as a follow-up in a fresh session, so decisions never pile into an old context. A lane that stops has either reported, posted an item it waits on, or still has work running; a silent stop gets nudged.
